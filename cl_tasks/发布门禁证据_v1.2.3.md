### 2.5 Release 构建 + 产物版本与哈希

```
$ cargo build --release
    Finished `release` profile [optimized] target(s) in 0.17s

$ (Get-Item .\target\release\quickpath.exe).VersionInfo
FileVersion    : 1.2.3.0
ProductVersion : 1.2.3.0

$ (Get-FileHash .\target\release\quickpath.exe -Algorithm SHA256).Hash.ToLower()
5d0ea7a88906219efea076c6929d481ddc85fdcd64d220b9bdb23dc4d71988b8
```

**关于这个 SHA-256 的适用范围（如实说明，防止被当成可验签的发布指纹）：**

- **工具间一致**：`certutil -hashfile target/release/quickpath.exe SHA256` 独立复算得**同一值**，两工具交叉一致。
- **同一输入状态可复现**：对同一提交连续做 3 次 `cargo clean -p quickpath && cargo build --release`，产物 SHA-256 **完全一致**（3/3 相同）。
- **但跨不同构建场合不保证一致**：同一提交在**另一次**构建时得到的产物哈希不同（本次整理过程中先测得 `f23ad729…3fcf`，随后强制 clean 重编得到 `5d0ea7a8…88b8`，两者均为同一源码的合法产物）。差异源于 PE/COFF 头部字段（本次实测 `TimeDateStamp = 1791959690`，**不是**固定 0）随构建场合派生。
- **因此**：发布侧的字节一致性依据必须是 **release workflow 每次运行现生成的 `sha256sums.txt`**（见 §2.6，已修复其恒为空的问题），而**不是**本文件记载的某个具体哈希值。本文件只把它作为「当时确实产出了可目视比对的具体产物」的现场证据。

（`certutil -hashfile target/release/quickpath.exe SHA256` 独立复算得同一值，两工具交叉一致。）

**关于 Authenticode**：本轮按用户决定**不启用**（报告 §4.3 已接受为发布残余）。因此本 SHA-256 只能证明**字节一致性**，**不能证明发布者身份**。

### 2.6 release workflow 打包与 SHA-256 清单 —— 发现并修复一处真实缺陷

**原实现（修复前）** `.github/workflows/release.yml`「整理打包产物与生成 SHA-256 清单」：

```powershell
Get-ChildItem -Path "dist" -File -Include "*.exe", "*.zip" | ForEach-Object { ... } | Out-File "dist/sha256sums.txt"
```

PowerShell 的 `-Include` **必须**配合带通配符的路径或 `-Recurse` 才生效。`-Path "dist"` 不含通配符、又未加 `-Recurse`，实测结果是**一个文件都匹配不到**，于是 `sha256sums.txt` 会**静默变成空清单** —— 而报告 §4.3 正是把这份清单当作「验证文件字节一致性」的兜底手段，空清单等于该兜底失效。

本机 5 组变体实测（`dist/` 内放置 3 个应打包产物 + 1 个故意放进去的杂散 `.txt`）：

| 变体 | 命令 | 命中数 |
|---|---|---|
| A | 修复前原样 `-Path "dist" -File -Include "*.exe","*.zip"` | **0** ❌ |
| B | 同上（相对路径，与 workflow 内一致） | **0** ❌ |
| C | `-Path "dist\*" -File -Include ...` | 3 ✅ |
| D | `-Path "dist" -File -Recurse -Include ...` | 3 ✅ |
| E | 不带 `-Include`，仅 `-File` | 4（把杂散文件也纳入）|

**修复**（提交 `d5793aa`）：改用 `-Path "dist\*"`，并新增 **fail-closed 守卫**——匹配结果为空时 `Write-Error` + `exit 1`，拒绝生成空清单：

```powershell
$artifacts = Get-ChildItem -Path "dist\*" -File -Include "*.exe", "*.zip"
if (-not $artifacts) {
    Write-Error "未能匹配到任何待校验产物（dist 为空或 -Include 未生效），拒绝生成空 SHA-256 清单"
    exit 1
}
$artifacts | ForEach-Object {
    $hash = (Get-FileHash -Path $_.FullName -Algorithm SHA256).Hash.ToLower()
    "$hash  $($_.Name)"
} | Out-File -FilePath "dist/sha256sums.txt" -Encoding ascii
```

**修复后本机等价复现**（同一含杂散文件的 `dist/`）：

```
命中数: 3
901b6aa0cd4e43f41a08a5bafaaddbef15a13256dc69fcd59d241faaa8a06ad8  QuickPath-v1.2.3-windows-x64.zip
f23ad72951d3a7aad8e76c135cb5bbed36b7122371144675d92adb9490573fcf  QuickPath-v1.2.3-x64.exe
f23ad72951d3a7aad8e76c135cb5bbed36b7122371144675d92adb9490573fcf  QuickPath.exe
```

> 注：上表哈希来自**当次**验证运行（该次 `dist/` 内的 exe 是当时 `target/release/quickpath.exe` 的副本）；后续强制 clean 重编后同一提交的产物哈希变为 `5d0ea7a8…88b8`。这正是本文件 §2.5 所述「跨构建场合哈希不保证一致」的现场例证——**职责上应由 workflow 每次现算清单**，而非依赖任何记载值。

杂散 `.txt` 被正确排除；空目录上守卫生效（走 `exit 1`）。清单中 exe 的哈希与 §2.5 中 `Get-FileHash`/`certutil` 的结果一致（同一份产物、两个工具互验）。

`release.yml` 变更后已通过 YAML 解析校验（PyYAML 6.0.3）。

**仍未验证**：该 workflow **尚未在 GitHub 上真实运行过**（需 `push` 一个 `v*` tag）。因此「打包—清单—上传资产」的端到端链路仍属**未验证**，本机只证明了脚本逻辑正确。
