## 3. P0-05 状态机模型（维护文档，防未来适配器绕开统一原语）

```
ClipboardSnapshot::capture()
  └─ 持锁期内读 capture_sequence（= “已存在内容”的序列号），绑定到快照
     capture_sequence == 0（不可读）→ 永不自动恢复（fail-closed）

【全仓唯一】clipboard_atomic_write(expected_sequence, empty_first, write)
  OpenClipboard(valid_owner)
    ├─ 持锁读 current_sequence
    ├─ current != expected → Close，返回 NotOwned，**零修改**
    ├─ current == expected →（可选）EmptyClipboard → write() 逐格式 SetClipboardData
    └─ CloseClipboard → 读 after_sequence
         ├─ 发生过修改（清空过 / 写入成功过 / after != expected）
         │    → 复核 GetClipboardOwner() 进程 == 本进程，否则 NotOwned
         └─ 返回 (after_sequence, 成功数, 失败格式)

ClipboardSnapshot::restore()
  for attempt in 0..3:
      pending = 尚未写回的格式
      atomic_write(expected, empty_first = !emptied, 写 pending)
        ├─ Ok((seq, .., failed=[])) → Restored（置 restored）
        ├─ Ok((seq, .., failed))    → expected = seq；emptied = true；
        │                             记录已写回格式；最后一轮仍失败 → Err(PartialRestore)
        └─ Err(NotOwned | Unknown)  → abandoned = true（永久放弃）
                                        → Abandoned，绝不清空/写入，Drop 也不补写

ClipboardTransaction::drop()
  ├─ outcome == RestorePartialFailure → 允许再补一次（仍走同一套持锁复核）
  └─ 其他终止态（Abandoned / AbortedEventHistoryUnprovable / Skipped*）
       → 绝不补写
```

**硬约束**：任何第三方管理器适配器**不得**绕过 `managers::clipboard_probe` 直接操作剪贴板；由
`clipboard_probe.rs::test_managers_delegate_clipboard_handling_to_transaction_probe` 与
`clipboard.rs::test_architecture_guard_single_atomic_clipboard_write_primitive` 两道源码扫描守卫强制。

## 4. P0-04-B 方案 B 的落地方式与实测依据

### 4.1 本机实测（决定了判据形态）

用临时探针（`test/scratch_clip_event_probe.ps1`，一次性文件，已删除）在真实 Win32 上测得：

| 场景 | 序列号增量 | `WM_CLIPBOARDUPDATE` 条数 |
|---|---|---|
| 同一 session（`EmptyClipboard` + `SetClipboardData`），消息泵实时 | **+5** | **1** |
| 仅 `SetClipboardData`（不清空） | +1 | 1 |
| 两个 session | +10 | 2 |
| 消息泵被阻塞期间两次 session，之后再统一处理 | +5 / +5 | **2**（两条都采样到最终序列号） |

**结论**：「一个 session ↔ 一条通知」是稳定规律；而序列号增量与环境/journal 有关（本机为 5），
**不可移植**。因此来源判据**不能**建立在「序列号增量 == 1」上，只能用「请求窗口内通知条数」。

### 4.2 由此落地的 fail-closed 规则

1. `probe_panel_path()` 在 `write_owned_text("")` 之后、`request_marker()` 之前调用
   `await_own_write_observed()`：等事件环追平自身写入序列号并**静默 5ms**，把本次事务自身那次
   写入的通知全部排空（否则它会落进请求窗口，把合法扫描误判为不可证明）。
2. `note_observed_owned_text_proven()`：序列号已变时要求
   - 事件环完整（未溢出、已追平当前序列号）；
   - 请求窗口内**恰好一条**事件；
   - 该事件的采样序列号 == 当前序列号；
   - 该事件与最终 owner 均被 `is_expected_source` 认可；
   任一不满足 → `OwnershipUnknown` 并把事务标记为 `AbortedEventHistoryUnprovable`，**绝不认领**。
3. 因此「阻塞消息泵 + 两次写入」必然登记两条事件 → 必然拒绝（M2 变异实测：放宽成「非空」后立刻错误认领）。

### 4.3 产品行为变更（需明确告知）

- TC / XYplorer 自动探测**默认关闭**；存量配置由一次性迁移 `clipboard_probe_opt_in_1_2_3` 置关，
  之后必须用户**显式开启**（写 `enable_totalcmd` / `enable_xyplorer`）。
- 开启后探测仍在后台扫描线程中执行（与清单 §2.4 「显式、前台、用户触发」的严格字面要求存在偏差：
  本轮的「显式」由用户手工改配置承担），**残余风险如实登记**，见 §5 第 2 条。
