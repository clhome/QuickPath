## 3. P0-04 状态机模型（维护文档，防未来适配器绕开统一协议）

```
begin()                     完整快照 + 初始 sequence（seq==0 → 归属已知不可判定）
  │
  ├─ write_owned_text(text)   【同一 OpenClipboard 持锁期内】：复核 seq==expected
  │                          → EmptyClipboard → SetClipboardData → CloseClipboard
  │                          → 读写入后 seq + 复核 owner 仍是本进程
  │                          任一不一致/不可读 → Err（fail-closed，不写入）
  │
  ├─ request_marker()        记事件环序号，作为「请求窗口」起点
  │
  ├─ request()               【外部】管理器写剪贴板（异步、不受本进程控制）
  │
  ├─ note_observed_owned_text_proven(marker, is_expected_source)
  │     新 seq == 旧 seq  → 归属未变（返回 None；管理器未写入）
  │     新 seq != 旧 seq  → 事件环必须完整（未溢出 + 已追平当前 seq）
  │                         且请求窗口内每次更新来源可归因
  │                         （本进程自己 / is_expected_source 认可的目标管理器）
  │                         且当前 GetClipboardOwner() 同属目标来源
  │                         否则 → Err(NotOwned / OwnershipUnknown)，绝不认领
  │
  └─ restore_if_still_owned() 严格 seq 校验 → Restored /
                              SkippedForeignChange / ReadFailed / RestoreFailed
                              （归属不可判定一律不写回旧快照）
```

**硬约束**：任何第三方管理器适配器**不得**绕过 `managers::clipboard_probe` 直接操作剪贴板
（快照 / 守卫 / 清空 / 恢复原语）。该约束由两个源码扫描守卫在编译期强制执行：
- `clipboard_probe.rs::test_managers_delegate_clipboard_handling_to_transaction_probe`
- `ipc.rs::test_each_enumerated_manager_window_is_verified_against_process_image`

## 4. 仍未关闭项（诚实清单）

1. **真机验收（报告 §6.6 最后两条 + §14）**：真实 `totalcmd.exe` / `xyplorer.exe` 双面板 1,000 轮高频复制、真实管理器卡顿/假死、人工操作节奏 —— 需装有第三方管理器的机器与人工执行（用户既定由其本人执行）。已补入 `Document/真机验收清单_竞态与生命周期_v1.2.3.md` §9（C-08~C-12）。
2. **事件链的固有极限**：`WM_CLIPBOARDUPDATE` 是**投递**消息，若两次剪贴板更新（如「用户复制」紧接「管理器覆盖」）在 owner 线程处理前被系统合并/延迟，第二次写入的 owner 读取可能已指向后写者，从而无法区分中间那一次。此时若最终 owner 恰为目标管理器，中间的用户内容仍可能被管理器自身覆盖（注意：**不是 QuickPath 写回的旧快照**）。这是 Windows 全局剪贴板协议层面无法根除的窗口；报告 §6.5 亦指出「若无法稳定提供这份证明，应避免用全局剪贴板作后台查询通道」。本轮的兜底是：**凡是无法证明的事件链一律 fail-closed，绝不认领**。
3. **目标管理器 owner 归属未知时的可用性**：若某管理器以 `OpenClipboard(NULL)` 写入（`GetClipboardOwner()` 返回 NULL）或经辅助进程写入，来源校验会失败 → 该管理器路径扫描被保守拒绝（功能降级、无数据破坏）。需真机确认 TC / XY 的实际 owner 行为。
4. **`AddClipboardFormatListener` 注册失败**：会让所有管理器探测 fail-closed（功能降级，已记 `CLIPBOARD_OWNER:` 诊断日志）。正常系统上该调用不会失败。
5. **fail-closed 的代价（诚实登记，自 P0-03 起的既定取舍）**：归属不可证明时 `restore_if_still_owned()`
   返回 `ReadFailed` / `SkippedForeignChange` 而**不回填旧快照**；由于用户事务前的原始内容已在清空步
   离开剪贴板，这同时意味着**旧内容不再回填**。取舍逻辑：宁可牺牲「旧内容回填」，也不可覆盖
   「可能是用户刚复制的新内容」。本轮的来源链校验使该分支比上一轮更易命中（例如目标管理器 owner
   不可归因时，见第 3 条），需在 C-10 真机验收中确认对正常跟随体验的影响。
6. **`cargo audit` 与 GitHub 侧**：`cargo audit` 仍须联网环境实跑；release workflow 未在 GitHub 实跑、发布环境审批保护未验证（沿用上一轮 O-02~O-04）。
7. **P2-1 Authenticode / P2-2 SBOM**：用户已决定本轮不启用签名；SBOM/RustSec DB 信息随附未做。
