## 1. §2 P0-03：第三方管理器扫描可能覆盖用户新复制内容

### 1.1 根因确认（§2.2）

**报告结论属实**，且本轮复核了更精确的机理：两个 manager 手工拼装 `ClipboardSnapshot::capture` + `ClipboardRestoreGuard::new` + `clear_clipboard_text` + `restore_now`，**从未调用** `note_temporary_write`，故 `owned_seq`/`owned_text` 恒为 `None`，`still_owned()` 对「未登记过临时写入」的状态直接放行恢复 → 用户新内容被旧快照静默覆盖。

补充事实（报告未展开）：同一轮扫描存在**两次**清空（源面板 + 副面板）与**多次**窗口枚举，因此「只让 `clear_clipboard_text()` 返回 sequence」这类局部修法确实不成立（报告 §2.4 的判断正确）。

### 3.1 执行 §3.2 时发现的**报告未察觉的真实缺陷**（重要事实修正）

报告 §3.2 称「静态审计确认 workflow 结构合理，但没有证明当前固定提交的实际运行结果」。**实际执行该 workflow 的打包逻辑后发现它并不合理**：

`release.yml` 原写作 `Get-ChildItem -Path "dist" -File -Include "*.exe", "*.zip"`。PowerShell 的 `-Include` **必须**配合带通配符的路径或 `-Recurse` 才生效；`-Path "dist"` 两者皆无，因此**一个文件都匹配不到** → 生成的 `sha256sums.txt` 是**空清单**。这直接击穿报告 §4.3 所依赖的「用 SHA-256 清单验证产物字节一致性」的兜底能力。

本机 5 组变体实测（`dist/` 内放 3 个应打包产物 + 1 个故意混入的杂散 `.txt`）：

| 变体 | 命令 | 命中数 |
|---|---|---|
| A | 修复前原样 | **0** ❌ |
| B | 同上（相对路径） | **0** ❌ |
| C | `-Path "dist\*" -File -Include ...` | 3 ✅ |
| D | `-Recurse -Include ...` | 3 ✅ |
| E | 不带 `-Include`，仅 `-File` | 4（杂散文件被误纳入）|

**修复（提交 `d5793aa`）**：改用 `-Path "dist\*"`，并新增 **fail-closed 守卫**（匹配为空 → `Write-Error` + `exit 1`，拒绝生成空清单）。修复后本机等价复现：恰好 3 个产物、杂散文件被排除、空目录上守卫生效。YAML 解析通过。

**仍未验证**：该 workflow **尚未在 GitHub 上真实运行**（需 `push` 一个 `v*` tag）。因此「打包 → 生成清单 → 上传资产」的端到端链路仍属未验证；本机只证明了脚本逻辑正确。

## 4. §4 P2 三项

### 4.1 owner ready 超时取消握手 —— ✅ 代码级关闭（提交 `b3923f6`）

**报告描述属实**（已核实：此处 "owner" 是 `src/win32/clipboard.rs` 的剪贴板 owner 线程，**不是** `src/tab/owner.rs`）。

| 报告建议 | 实现 |
|---|---|
| ready 超时时设置共享取消标记 | `Arc<AtomicBool>`，spawn 前创建、移入线程体；超时路径 `cancel.store(true)` |
| 线程在注册窗口类后、创建窗口前、进入消息泵前检查取消状态 | 三个检查点齐备；检查点 1/2 命中即退出且不创建窗口；检查点 3 命中走 `DestroyWindow`（触发既有 `WM_DESTROY → PostQuitMessage`）并按 `hwnd_raw` 比对后清空 `OWNER`，**不进入消息泵** |
| 已创建窗口时走正常 `WM_CLOSE → WM_DESTROY → WM_QUIT` | 超时路径 `ready_rx.try_recv()` 接住「迟到 ready」，按既有协议回收（`WM_CLOSE` + `PostThreadMessageW(WM_QUIT)` 兜底） |
| 增加「迟到 ready」「超时取消」「取消与创建并发」的测试 | 3 个用例齐备，经**通道会合**驱动（无 sleep 猜时序），仅注入 50ms 短超时以触发 `recv_timeout` |

**超出报告要求的加固**：超时路径由「直接丢弃 `JoinHandle`（detach）」改为「置取消 → 回收迟到窗口 → `done_rx.recv_timeout(2s)` 有界确认后 `join`」。

**如实登记的残余风险**：若 `CreateWindowExW` 或其前置调用在真实环境挂起 > 2s，线程尚未抵达任一检查点，取消不会被执行 → 有界确认超时 → 记 `CLIPBOARD_OWNER_TIMEOUT_CANCEL`（明确标注残余风险）后仍 detach。判定为**非阻塞**（单次 `CreateWindowExW` 正常为微秒级；报告 §4.1 本身即定为「概率低、不阻塞当前版本」），已列入真机观察点。

## 8. 报告未列出、但本轮一并修复的**同族缺陷**（用户要求「发现共性问题也要一起修」）

| 缺陷 | 机理 | 提交 |
|---|---|---|
| 宿主消息循环 `GetMessageW(...).as_bool()` 错误态死循环 | `GetMessageW` 返回三态 `BOOL`（>0 / 0=WM_QUIT / **-1=错误**），`BOOL(-1)` 非零 → 判真使循环在消息队列出错时**无限空转且永不退出**，整套退出清理链（`HOST_HWND` 置空、`UnregisterHotKey`、`AppState` 回收、owner 关闭、`CoUninitialize`）全部走不到 | `2357ea6` |
| `tab/coordinator.rs` 对 Explorer 使用**无超时**的跨进程 `SendMessageW` | Explorer 挂起→工作线程永久阻塞，且此时被接管的新窗口已被置全透明并移出屏幕 → 用户看到「点了完全没反应」，失败卫兵链永不到达。改走既有 `ipc::send_message_timeout`（有界 + `SMTO_ABORTIFHUNG`） | `2357ea6` |
| 两 manager 的进程镜像核对**只作用在首个命中窗口** | 枚举链中后续同类名伪装窗口照样收到 `WM_COMMAND` / `WM_COPYDATA`（违反 P-03「不得向伪装窗口发送协议消息」）→ 改为循环内逐窗口核对 | `2357ea6` |
| STA worker 线程创建失败用 `.expect(...)`（`panic = "abort"` 下终止整个托盘程序）；scanner worker spawn 失败被静默吞掉（后台扫描静默永久不启动） | 两处都属「线程创建失败未 fail-safe」：前者经 `host_wnd_proc → dispatch → try_rebuild → make_worker` 可达；后者先置 `WORKER_STARTED=true` 再丢 `spawn` 结果 | `40ce6d7` |

以上 4 项均带**源码扫描式守卫测试**（防止再犯）+ **变异自证**（改坏必红，由父 agent 独立复现）。测试总数 **161 → 171**。
