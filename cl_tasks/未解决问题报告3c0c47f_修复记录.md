## 2. 缺陷确认(报告描述与代码逐一吻合)

修改前的实现:

```rust
// try_acquire_fingerprint 内
if state.generations.len() > 16 {
    state.generations.clear();          // ← 清表
}
let generation = state.generations
    .entry(fingerprint.to_string())
    .or_insert(0);                       // ← 清表后同一指纹又从 0 开始
*generation = generation.wrapping_add(1);
```

`try_acquire_restore` 只比较**数值**是否相等,因此无法区分「清表前的旧 `1`」与「清表后的新 `1`」——
状态经历了变化但数值变回原值,即 **ABA**。报告给出的确定性触发链(N 个对话框跨过 16 项边界,
再在 650 ms 窗口内对同一对话框执行注入 B)在代码上完全成立。

**另外一处报告点名的问题同样确认**:修改前的 `generation()` 是 `current_generation(&self.fingerprint)`
—— 即「主注入结束后**回查映射**」,正是报告 P1-09 第 2 节要求禁止的写法
(映射被回收时会拿到缺失/错误的值)。已一并修掉。

## 3. 落地:进程级单调令牌(按报告推荐方案)

`src/win32/uia.rs`:

1. **发号器与映射拆开**(`WpsInjectState`):
   ```rust
   struct WpsInjectState {
       holder: Option<String>,
       generations: HashMap<String, u128>,
       next_generation: u128,   // 进程级单调,清表绝不触碰
   }
   ```
2. **主注入从全局发号器取令牌**;发号 → 清表 → 写映射 → 登记 holder 全部在**同一临界区**:
   ```rust
   state.next_generation += 1;
   let generation = state.next_generation;
   if state.generations.len() > 16 { state.generations.clear(); }  // 只限制内存
   state.generations.insert(fingerprint.to_string(), generation);
   ```
   ⇒ 清表**不可能**让新令牌等于旧令牌,ABA 被结构性消除。
3. **类型升为 `u128`**:彻底消除回绕(即便每纳秒发一次号也远超任何物理时间尺度),
   因此不需要额外的「回绕 fail-closed」分支。`0` 继续作为「无记录」哨兵
   (发号器从 1 开始),这也让 fail-closed 语义明确。
4. **lease 持有不可变令牌**:`WpsInjectLease { fingerprint, generation }`,
   `generation()` 直接返回构造时保存的值,**不查映射**。
5. **恢复入口保持原子条件取得**:同一把锁内校验「无 holder」+「令牌指中」+ 登记 holder;
   刻意**不推进发号器**;取不到即零动作退出(不建 UIA 客户端、不查控件、不抢焦点、不碰剪贴板、不发按键)。
6. **两层 lease 未动**:`WpsInjectLease`(WPS 操作链)与 `ClipboardTransaction` 私有 lease(系统剪贴板)
   保持独立,刻意不合并;P1-08 建立的条件式恢复入口完整保留。

`current_generation()` 已降为**仅测试使用**(`#[cfg(test)]`)并移入测试模块 ——
生产路径不再有任何「自己会加锁的令牌读取助手」可被误用于锁外检查。

## 4. 测试(报告 §回归测试 的 10 步序列 + 既有不变量)

### 4.1 `test_generation_token_is_process_monotonic_across_map_eviction`

严格按报告 10 步序列实现,并额外让每个断言都有反例意义:

| 报告步骤 | 本用例断言 |
|---|---|
| 1 预填 16 个不同 fingerprint | 断言映射恰好 16 项、发号器恰好前进 16 |
| 2 对新指纹 F 取得 token A(表长→17) | 断言此时映射 17 项(已越过上限) |
| 3 释放 lease | — |
| 4 再次对 F 取得 token B(强制走清表分支) | 断言清表后映射只剩 1 项 |
| 5 `token_b != token_a` | **核心断言**,直接对应旧实现的 ABA |
| 6 释放主注入 lease | — |
| 7 用 token A 取恢复 → 必须失败 | 断言 `is_none()` |
| 8 用 token B 取恢复 → 空闲时必须成功 | 断言 `is_some()` |
| 9 恢复取得不修改 `next_generation` | 断言发号器值前后相等 |
| 10 清表前后 `next_generation` 严格前进 | 断言 `after_evict > after_prefill` 且 `token_b == after_evict` |

补充:被清掉的旧指纹(映射中已无记录)必须 fail-closed。
说明:令牌计数是**进程级**的,故所有断言一律用相对值(用例开始时先清映射并记录 `base`)。

### 4.2 `test_lease_carries_immutable_token_not_a_map_lookup`(报告 P1-09 第 2 节)

取得 token → 人为把该指纹从映射中抹掉(模拟容量回收)→ 重新取得必须得到**全新**令牌,
证明令牌不来自查表、发号器不受映射删除影响。

### 4.3 既有不变量全部保留

- holder 被占用时新旧操作都不得穿透 → `test_restore_lease_is_conditional_atomic_...`、`test_restore_cannot_slip_through_...`;
- fingerprint 不同也必须互斥 → `test_wps_inject_lease_is_exclusive_...`(跨指纹断言);
- 恢复提前返回 / panic 展开后 RAII 释放 → 同用例(`catch_unwind` 段);
- P0-07 剪贴板事务仍在读取原剪贴板前取得独占 lease → 既有 P0-07 全部用例保持不变。

### 6.1 M5 的诚实边界(重要,不掩盖)

M5 **只被源码守卫抓住**,行为用例没有红。分析结论:**这在结构上无法由行为层钉住** ——
正确实现里「令牌比较」与「holder 占位」位于同一临界区,根本不存在可供测试插入的「两步之间」窗口;
而 M5 造出的锁外窗口宽度为「一次加锁-解锁」,用 `sleep` 无法稳定命中(会变成 flaky 测试)。
本轮尝试补一个行为用例(`test_restore_token_check_cannot_be_satisfied_by_stale_token`)
后发现它只是重复既有覆盖、并不能提高对 M5 的敏感度,按 KISS 原则**未保留**该用例。

⇒ 结论如实登记:M5 由**源码守卫**保证(断言该函数体内必须出现
`state.generations.get(fingerprint)` 且**不得**出现自会加锁的 `current_generation()`,
并断言状态锁取得语句早于两处校验),而不是由行为用例保证。

### 6.2 本轮踩到并修正的工具陷阱

- **变异脚本的 `assert` 未命中导致变异未生效**:第一次执行 M1 时 python 脚本因 rustfmt 折行
  未匹配到目标文本而抛错,**文件未被修改**(此时 228 全绿),导致我把「M1 已应用」当成事实。
  后续每次都先用 `grep -n MUTATION src` 核对,并在还原后确认 `grep` 输出为空。
  **教训:变异自证必须核对「变异真的落盘了」,不能只看测试结果。**
- **守卫的切分标记会随改名失效**:`test_wps_injection_wires_...` 原用注释
  `"    /// 该对话框当前的注入代次"` 作为函数结束标记,本轮改名后该标记不再存在,
  `.unwrap_or(restore_tail.len())` 便**静默**把整个剩余源码当作函数体 → 守卫误报。
  已改为按 `"\n    fn "` 这一**稳定语法边界**切分,并把 `.unwrap_or(...)` 换成 `.expect(...)`。
  **教训:守卫的区间边界必须用语法结构而不是注释文案;兜底一律 fail-loud 而不是静默变宽。**
